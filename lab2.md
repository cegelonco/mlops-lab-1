## Question 2

### What is `--backend-store-uri` used for? What is `--default-artifact-root` used for? What is the difference between metadata and artifacts?

`--backend-store-uri` specifies where MLflow stores experiment and run metadata.

In this lab, the metadata is stored in a SQLite database:

`mlflow.db`

This metadata includes information such as experiment names, run IDs, parameters, metrics, run status, and timestamps.

`--default-artifact-root` specifies where MLflow stores artifacts generated by experiments.

In this lab, the artifact directory is:

`./mlruns`

Artifacts are files produced during a run, such as trained models.

Therefore, metadata describes the experiment and its results, while artifacts are the actual files generated by the experiment.

## Question 3

### Why shouldn't `mlflow.db` and `mlruns/` be tracked by Git? Why shouldn't they be tracked by DVC either?

`mlflow.db` and `mlruns/` are generated locally while experiments are executed.

They should not be tracked by Git because they change frequently, can become large, and are not source code.

They should also not be tracked by DVC because MLflow is already responsible for storing experiment metadata, metrics, and model artifacts.

In this project, DVC is mainly used for versioning the datasets, while MLflow is used for tracking machine-learning experiments.

## Question 4

### What happens the first time `mlflow.set_experiment()` is called with a name that does not exist?

When:

`mlflow.set_experiment("food11")`

is called for the first time, MLflow checks whether an experiment named `food11` already exists.

Since it does not exist, MLflow automatically creates it.

The new `food11` experiment then appears in the MLflow UI, and the following training runs are associated with this experiment.

## Question 5

### What is the difference between `mlflow.log_param` and `mlflow.log_metric`? Why does `log_metric` take a `step` argument?

`mlflow.log_param` is used to record configuration values that are fixed for a training run.

Examples include:

- learning rate
- batch size
- number of epochs
- model architecture
- dataset

`mlflow.log_metric` is used to record numerical results generated during or after training.

Examples include:

- training loss
- validation loss
- validation accuracy
- test accuracy

A metric can change during training, so `log_metric` accepts a `step` argument. In this lab, the step corresponds to the epoch number and allows MLflow to display how a metric evolves during training.

A parameter does not need a step because it normally remains constant throughout the run.

The trained ResNet18 model was logged as an MLflow model artifact.

`--default-artifact-root ./mlruns`

## Question 7

### Which learning rate gave the best `val_accuracy`? Is higher always better?

Several runs were compared using different learning rates.

The learning rates tested were:

- `0.01`
- `0.001`
- `0.0001`

The learning rate `0.001`, with a batch size of `32`, produced the highest validation accuracy of approximately `0.729`, or 72.9%.

A higher learning rate is therefore not always better.

In this experiment, using `lr = 0.01` resulted in a very low validation accuracy of approximately 14.7%.

A learning rate that is too high can make the optimizer update the model weights too aggressively and prevent good convergence.

## Question 8

### What pattern can be seen in the parallel coordinates plot?

The parallel coordinates plot shows a clear relationship between the learning rate, batch size, and validation accuracy.

The best result was obtained with:

- `lr = 0.001`
- `batch_size = 32`

This configuration achieved a validation accuracy of approximately 72.9%.

The higher learning rate of `0.01` produced the worst result, with validation accuracy around 14.7%.

The smaller learning rate of `0.0001` performed better than `0.01`, but it still did not perform as well as `0.001`.

The comparison also showed that increasing the batch size from `32` to `64` while keeping the learning rate at `0.001` reduced the validation accuracy.

Therefore, among the tested configurations, `lr = 0.001` and `batch_size = 32` produced the best result.
